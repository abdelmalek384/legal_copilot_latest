# Fictional-client end-to-end acceptance scenario

**Status:** scenario specification only. No browser, API, lawyer, security, or operational acceptance is claimed. All names, identifiers, events, and documents below are fictional test data.

## 1. Purpose

Exercise one synthetic client's matter from firm onboarding through document intake, review, retrieval, legal-research handoff, collaboration, export, and cross-firm denial. This scenario complements the [manual acceptance runbook](manual_acceptance_runbook.md), route-level security tests, legal-source review, and production recovery drills.

Run against one pinned build in an isolated staging environment. Use disposable databases and private test object storage. Disable external email delivery, payment gateways, and real-client integrations unless a separately approved staging exercise explicitly requires them.

## 4. Execution sequence and acceptance assertions

For every step, record PASS, FAIL, or BLOCKED, the exact build SHA, test account role, timestamp/timezone, and sanitized evidence reference. A step is PASS only when its observable assertions and evidence are complete.

### A. Sign-in, onboarding, and firm context

1. Sign in as Firm A admin.
   - Expected: authenticated session is established; the selected firm is Cedar & Nile Legal; session and CSRF cookies have the configured production-like attributes.
   - Expected: setup health reports configuration facts without exposing secrets, file paths, tokens, or credential values.
2. Complete the synthetic firm profile and first-run checklist using non-deliverable test values.
   - Expected: profile changes are limited to Firm A; onboarding state is recorded once; no live reminder is sent.
3. Verify MFA enrollment/verification behavior for the active policy.
   - Expected: required users cannot access protected matter routes before enrollment/verification; recovery codes are displayed once and stored only as hashes.
4. Switch to Firm B only after creating a separate test membership.
   - Expected: the switch response immediately reports Firm B's MFA state; the next session read and protected route agree with the destination firm.
   - Expected: switching back to Firm A restores Firm A context without carrying over another firm's role.

### B. Matter creation and collaboration

5. As Firm A admin, create the fictional client/matter using the identifiers above.
   - Expected: matter is visible in Firm A only; case number, year, court/circuit fields, stage, and opposing-party fields retain the submitted values.
6. Sign in as Firm A lawyer and junior.
   - Expected: matter visibility follows explicit membership and role policy; junior cannot perform lead/admin-only actions.
7. Sign in as Firm B lawyer and attempt to open Firm A matter using the known synthetic matter ID.
   - Expected: response is denied without disclosing whether the matter exists or returning any matter metadata.
8. Repeat the denial against document IDs, chunk IDs, annotations/notes, search parameters, exports, and any child-resource routes available in the pinned build.
   - Expected: authorization is enforced server-side for direct identifiers and alternate methods; no cross-tenant content appears in response bodies, errors, logs, or exports.

### C. Upload, extraction, and original-file integrity

9. Upload the four valid synthetic documents to the Firm A matter.
   - Expected: each upload is bound to the correct firm and matter; metadata includes uploader, timestamp, content type, byte size, and content digest as implemented.
   - Expected: extraction status is explicit; unsupported, encrypted, malformed, oversized, or resource-exhausting inputs fail closed with a safe message.
10. Compare each stored original's digest and byte size with the pre-upload manifest.
    - Expected: retained originals match exactly; downloads enforce authorization and integrity checks; failed integrity checks do not produce a successful download audit event.
11. Upload the invalid/oversized fixture.
    - Expected: rejection occurs at the configured limit; no partial document, chunk, or original object is left behind.
12. Review extraction results against the synthetic originals.
    - Expected: OCR/extracted text is visibly unverified; the UI does not imply that extraction proves authenticity or legal correctness.

### D. Document review, annotations, and notes

13. Open the detailed document-review panel for the mock agreement.
    - Expected: original/extracted text and extraction-time page metadata are distinguishable.
14. Add a reviewer page reference and a review note to one passage; accept another passage; mark a third for re-check; correct a fourth passage.
    - Expected: the current reviewer-entered page reference is submitted for every outcome; blank remains blank when not supplied.
    - Expected: reviewer-entered references are stored in review history only and never overwrite extraction-time chunks.page.
    - Expected: corrected text is versioned/audited and stale source digests are rejected.
15. Repeat the same review actions through the compact queue.
    - Expected: the compact queue offers the page-reference input and submits its current value for all outcomes.
    - Expected: if more than 100 eligible passages exist, a visible notice explains the render cap and directs the reviewer to the full document panel.
16. Add a document annotation/highlight and a matter note using synthetic text.
    - Expected: each item is associated with the intended document/matter and actor; another firm cannot retrieve it; edit/delete permissions follow the role policy.
17. Reload the page and sign out/in.
    - Expected: persisted review events, annotations, and notes reappear with correct attribution and no duplicate writes.

### E. Client-wide retrieval and legal-research handoff

18. Search Firm A's accessible extracted documents using distinctive synthetic Arabic and English phrases.
    - Expected: results include only Firm A documents accessible to the user; equal-ranked results paginate deterministically; pagination does not duplicate or skip stable results.
19. Repeat with Firm B lawyer and with a guessed Firm A matter/document identifier.
    - Expected: no Firm A passage, filename, citation, snippet, count, or metadata leaks.
20. Open the legal-research workspace from the matter.
    - Expected: legal corpus results remain separate from client-uploaded evidence; source status, version, permission, and verification labels remain explicit.
21. Ask one neutral synthetic question that can be answered only from the approved test corpus and one question whose test corpus is deliberately insufficient.
    - Expected: supported statements cite the supplied sources; insufficient evidence produces an explicit abstention/uncertainty; uploaded matter text is treated as untrusted evidence, not as instructions.
    - Expected: no fabricated statute, article, deadline, case citation, or legal conclusion is accepted as a passing result.
22. Save a research note/memo to the matter.
    - Expected: the saved artifact belongs to Firm A and the intended matter; source references and uncertainty labels are retained.

### F. Deadlines, communications, and export

23. Add a fictional procedural reminder using a clearly labelled test date.
    - Expected: date validation rejects impossible dates; no real email or external reminder is delivered; reminder ownership and matter scope are correct.
24. Add a synthetic communication entry and verify its audit/history behavior.
    - Expected: actor, time, matter, and content are associated correctly; unauthorized roles cannot mutate it.
25. Export Firm A's data using the authorized admin path.
    - Expected: archive contains only Firm A records and permitted fields; CSV formula-like cells are neutralized; no password hashes, session tokens, MFA secrets, recovery hashes, invitation tokens, or recovery tokens are exported.
26. Attempt the export as Firm A lawyer/junior and Firm B lawyer.
    - Expected: role denial and tenant denial are enforced; no archive is produced for unauthorized requests.

### G. Session revocation and negative-path checks

27. Revoke/disable the Firm A junior membership while the junior has an active browser session.
    - Expected: the next protected request is denied; already-open tabs cannot continue reading or writing matter data.
28. Log out and replay the prior session cookie.
    - Expected: session is rejected and auth cookies are cleared; state-changing requests still require CSRF/origin validation.
29. Exercise expired-session, revoked-membership, suspended-firm, malformed-ID, and oversized-body cases.
    - Expected: fail-closed responses; no stack trace, SQL detail, secret, or cross-tenant existence signal.

### H. Browser and device acceptance

30. Repeat the core journey in Arabic RTL and English LTR on desktop Chrome and Edge, macOS Safari, physical iOS Safari, and physical Android Chrome.
    - Expected: direction, punctuation, mixed Arabic/Latin identifiers, focus order, tables, dialogs, notes, citations, and upload controls remain usable.
31. Complete the core journey with keyboard only and with the designated screen readers.
    - Expected: accessible names, roles, values, validation errors, focus movement, loading states, and action outcomes are announced and operable.
32. Test physical-device portrait/landscape, zoom, touch targets, and offline/failed-network recovery.
    - Expected: no essential action is hidden, duplicated, silently lost, or dependent on hover.

## 6. Release decision

- Any cross-firm disclosure, authorization bypass, secret exposure, original-file integrity mismatch, silent data loss, or unsafe export is an immediate FAIL and blocks the pilot.
- Any unexecuted required step is BLOCKED, not PASS. A source-code assertion or test authored without execution is not acceptance evidence.
- This scenario does not verify legal-source authenticity, rights to reuse legal content, legal advice quality, production security, backups, or restore capability. Those remain separate sign-off gates.
- A pilot decision requires exact-head runtime results, manual lawyer acceptance, physical-device/accessibility evidence, Egyptian-counsel legal acceptance, and witnessed operational recovery. Do not onboard real client data until those gates are independently closed.
